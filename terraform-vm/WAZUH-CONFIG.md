# wazuh-homelab — Application Configuration (terraform-vm path)

This document covers **Wazuh application-layer configuration** on the
Terraform/libvirt VM — everything that happened *after* the VM was up
and reachable. For provisioning the VM itself (Terraform, cloud-init,
networking, access path), see [`README.md`](./README.md).

For agent enrollment, the OPNsense plugin, and syslog forwarding — the
steps that apply regardless of which deployment path stood up the
manager — see [`../docs/post-deployment.md`](../docs/post-deployment.md).
This file only captures what's specific to *this* install: real
timestamps, the actual IP, and any real problems hit along the way.

## Prerequisites

- VM up and reachable — see README's "Current working access path" (SSH
  via another VM on the host, e.g. Windows11 → the VM's DHCP-assigned
  IP).

## 1. Install Wazuh (all-in-one)

Installed via Wazuh's official install assistant script, all-in-one mode
(`-a` flag — indexer + manager + dashboard together on the single VM,
matching the monolithic architecture decision in `README.md`):

```bash
curl -sO https://packages.wazuh.com/4.14/wazuh-install.sh
sudo bash wazuh-install.sh -a
```

- **Version installed:** 4.14.7
- **Duration:** ~3 minutes, start to finish (14:31:31 → 14:34:37)
- **Result:** clean install, no errors. All phases (indexer → manager →
  filebeat → dashboard) completed and started successfully on first try.
- **Web interface:** port 443 (default), `https://192.168.10.13`
- **Initial `admin` password:** generated by the installer, shown once in
  its final summary output, captured and stored in 1Password immediately.
  Not repeated here on purpose.

Verified all three services `active (running)` via:
```bash
sudo systemctl status wazuh-indexer wazuh-manager wazuh-dashboard
```

A few `error`-tagged lines appeared in `journalctl -u wazuh-dashboard` and
`wazuh-cluster.log` during startup — all benign, not indicative of a
broken install:
- Two `ResponseError` lines from an earlier dashboard process instance
  (PID `61770`) that exited when the install script restarted the
  dashboard mid-configuration — not the actual running process.
- One `401` on the monitoring plugin — startup race, the plugin polled
  the API before internal auth/keystore setup finished; self-resolved.
- One `resource_already_exists_exception` for the `wazuh-statistics`
  index — two init routines racing to create the same index; harmless,
  the index exists either way.

**Reboot completed.** `apt update` afterward showed all packages already
current — the restart-required flag was cleared by this reboot. All three
services confirmed `active (running)` again post-reboot, with clean
startup logs this time (no `error`-tagged dashboard log lines, unlike the
first boot) — confirms the earlier startup-race errors were genuinely
one-time init noise, not a recurring issue.
